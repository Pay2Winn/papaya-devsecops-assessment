# DevSecOps with coding agents at Papaya

## Scope and evidence

**Source:** [DevSecOps Challenge 1 — DevSecOps with Coding Agents at Papaya](https://github.com/papaya-insurtech/pumpkin/blob/main/Hiring/DevSecOps_Challenges/DevSecOps_Challenge_1.md), including Appendix A. This is a proposed target operating model, not an assessment of Papaya's actual controls. I have no access to its systems, code, contracts, or production data. No control below is claimed to exist or to establish certification or legal compliance.

**Explicit challenge requirements:** use a coding agent; design a framework and workflow for agent-assisted DevSecOps against the stated platform and opposing engineering/compliance positions; submit deliverables and *complete, raw, unedited* conversations from every agent session in one GitHub repository. The prompt leaves deliverable format open. It does not require deployment or proof of existing compliance.

**Working assumptions to validate:** Papaya can separate production from non-production identities and isolate production deployment credentials; a central identity provider can supply named human accounts with multi-factor authentication; GitHub branch protection, environments and workload federation are available under the organization's plan; infrastructure definitions and service deployment workflows can be brought under review; each partner's residency, retention, disclosure and breach-notification requirements must be mapped with counsel and partner owners. Where a platform cannot enforce a gate, block that deployment path until an equivalent control exists rather than treating a written policy as enforcement.

**Decision:** agents may diagnose and propose changes, but are never production approvers or holders of production write credentials. In production, an agent is **read-only even after a DevOps approval**: it cannot create, modify or delete resources or data. A named, independent human reviews the specific revision and production plan; a separately gated deployment identity applies only that revision. Engineering keeps a fast path to read-only diagnostics and staging. Compliance gets a technical boundary on production writes. A click alone is insufficient: authorization, artifact identity, isolation, audit and rollback must also hold.

## Trust boundaries and enforcement

| Boundary | Proposed enforcement | Failure behavior |
| --- | --- | --- |
| Engineer laptop and agent | Remove standing production write roles from human single sign-on profiles. Give the agent only a controlled telemetry gateway with a filtered, tenant/region-scoped, read-only interface; no production shell, database administrator role, unrestricted cloud command-line interface or deploy credential. Authenticate the engineer's gateway session through the identity provider using OpenID Connect (OIDC) and short-lived tokens; the gateway uses its own scoped workload identity to read telemetry, never a long-lived key or the engineer's production cloud profile. Validate token issuer, audience, expiry and engineer authorization at the gateway. Human diagnostic access, if needed, is time-limited and named. Put production write behind organization/account/project identity controls, not prompts, shell aliases, repository instructions or an agent's self-report. | A laptop with prompts disabled can still edit local code, but the agent cannot mutate production or use the deployment identity. Block or expire diagnostic access if identity or device requirements fail. |
| Agent extensions and data | Maintain a reviewed, version-pinned allowlist for Model Context Protocol (MCP) servers and plugins; assess code, dependencies, tool permissions, network destinations and update provenance in an isolated test environment. Default deny unreviewed extensions for work involving company code or data; enforce on managed endpoints and controlled runner images, not just in agent configuration. Treat partner documents, logs, issue text, repository files and tool outputs as untrusted instructions. | An unreviewed server/plugin gets no company data or credentials. A prompt-injected document cannot authorize a tool or workflow. |
| Source and review | Protect default and production branches: required status checks, up-to-date reviewed changes, no direct pushes, no force push or routine administrator bypass, CODEOWNERS for infrastructure/security paths, independently named human reviewer(s), and stale-review dismissal on new commits. Protect workflow, CODEOWNERS and policy files with security-owned review. Restrict bot permissions; an agent identity cannot count as a human approver. | No merge if a review, check or protected-file ownership gate fails. Audit exceptional administrative bypass separately and investigate it. |
| Continuous integration and deployment | Separate untrusted pull-request checks from trusted planning and deployment workflows. Run pull-request jobs with read-only repository token, no cloud secrets, and isolated runners; never run untrusted pull-request code in a privileged `pull_request_target` or equivalent context. A protected-revision planning job may obtain a separate short-lived, production **read-only** identity. A production deployment job obtains a distinct short-lived **write** identity only after its protected-environment approval. Use GitHub OpenID Connect (OIDC) federation: the job requests an identity token (`id-token: write`, scoped to that job), then exchanges it for short-lived AWS role or Google Cloud workload-identity credentials; cloud trust must restrict audience and claims to the intended repository, protected branch and production environment/workflow, and IAM must scope permitted actions and resources. The GitHub token permission to request an OIDC token is not itself cloud write permission. For k0s and Firebase, use a broker or supported identity-federation path that issues only short-lived, scoped credentials; do not pretend GitHub OIDC directly authenticates to an unconfigured cluster or release endpoint. Inventory and rotate existing long-lived repository AWS keys and GitHub personal access tokens, migrate each consumer, then revoke and remove the old secrets. Pin third-party actions to reviewed immutable references. | A pull request cannot obtain production credentials. A write job cannot assume a role if claims, audience, repository, ref or environment do not match. |
| Secret storage | Keep sensitive secret values in a managed vault: AWS Secrets Manager for AWS, Google Cloud Secret Manager for Google Cloud, and Azure Key Vault only if Azure workloads are introduced. Store references, not values, in source, infrastructure state where avoidable, GitHub settings, logs or agent prompts. Grant retrieval to the specific runtime/deploy identity, audit reads and rotate on exposure; use OIDC federation instead of storing cloud access keys. | Missing vault access blocks the workload; never fall back to a repository secret or a hard-coded value. |
| Production approval and cloud authority | Configure a protected production environment with required named reviewers and self-review prevention; only the trusted deployment workflow may request its write credential. Bind deployment to the reviewed commit, immutable build artifact digest, tenant/region and plan hash. Give the deploy principal least-privilege, scoped production write permissions; deny routine human/agent write paths at the AWS organization/account and Google Cloud organization/project identity boundaries where feasible, with monitored exception roles. The agent identity is permanently read-only, including during incidents; approval of a diagnostic command changes only access to that command, never its privileges. Restrict k0s administration and Firebase release authority to controlled deploy identities. | No direct laptop apply, missing approval or changed plan can deploy. Emergency operator identity is separate from the agent, short-lived, logged, independently approved before use and reviewed again afterward. |

These gates need an adversarial test: attempt a direct laptop production write, a pull-request job credential request, an altered workflow, a self-approval, a commit pushed after approval, and a changed infrastructure plan. Each must fail at the relevant control plane. GitHub configuration alone does not stop a separately privileged cloud user; cloud identity and organization restrictions must close that route. Likewise, an OIDC role trust policy alone does not make a compromised runner harmless: keep runners ephemeral/isolated, scope roles tightly, and monitor their sessions. Configuration drift, cloud consoles, k0s credentials and Firebase release tokens are parallel write paths that must be inventoried and closed or documented as explicitly governed exceptions.

## Normal production change: end-to-end

1. **Request and classify.** Open a Linear change record with business owner, service, partner/country/region, data classification, intended behavior, risk, maintenance window, test and rollback owners. Before any production change, document the affected data/resources, the applicable backup or snapshot and its retention/location, how to verify recoverability, the exact rollback or forward-recovery steps, trigger and responsible operator; check restoration feasibility for irreversible migrations. If no relevant data is at risk, explain why a data backup is not applicable and still provide a configuration/artifact recovery plan. Check contractual residency and partner notification requirements; do not include medical records, identifiers, bank data or secrets in tickets, prompts, pull requests or build logs. Define success and abort signals before work starts.
2. **Develop and diagnose.** Before each agent task, the agent sends the designated human requester a short summary of its objective, intended tools, data/production scope and proposed actions; it waits for that person's explicit, recorded approval. Any expanded scope requires a new summary and approval; at completion it sends a result summary. A controlled agent runner must enforce this task gate even if local permission prompts are disabled; without that runner, this is only a proposed policy, not a guarantee. This task approval is **not** independent production change approval or permission for production writes. The engineer then uses the agent against synthetic/redacted fixtures, staging, and a scoped, read-only production telemetry gateway when needed. The gateway enforces tenant/region filters, approved query templates, output redaction, query budgets and an audit trail; it never hands the agent a production shell or write credential. Repository and tool outputs are data, not instructions. If the agent asks to run a production write or use an unknown MCP server/plugin, stop that route; cloud and network boundaries must still deny it. Record material agent-assisted changes in the pull request for reviewer context, without assuming the agent is an approver.
3. **Pull request.** Link the Linear record; provide architecture impact, partner/region scope, migration and backward-compatibility notes, threat considerations, test evidence, proposed infrastructure diff, rollout schedule, monitoring and rollback. Require separate human review by the relevant service owner and, for production identity, data-boundary or infrastructure changes, the security/platform owner. The author and agent cannot satisfy independent approval. Escalate high-risk cross-border or sensitive-data changes to the appropriate privacy/partner owner before deployment.
4. **Untrusted checks.** In isolated pull-request continuous integration, run relevant TypeScript/Node.js and Python tests, lint/type checks, migration tests, offline infrastructure validation/preview, secret scanning, dependency/container/image scanning, infrastructure-as-code policy checks and targeted security tests. Block on defined severity thresholds or require a time-bound, named exception with compensating controls; never silently waive findings. Validate Pulumi policy constraints and Serverless Framework package/configuration; test GraphQL authorization and tenancy boundaries when touched. Tests use synthetic data and no production credentials. Publish artifacts and findings with restricted visibility and redacted logs.
5. **Plan A and independent approval.** The agent drafts a change; after pull-request checks and review, the protected-revision pipeline builds one immutable artifact and generates production plan A with a separate read-only planning identity. A named reviewer independent of the change author inspects the source diff, tests, artifact identity, exact resource/data-access operations, tenant/region impact, backup/recovery evidence and rollback steps before approving A; missing or unverified recovery evidence blocks approval. A protected approval service stores their authenticated approval as an append-only record bound to the commit, production environment, artifact digest and plan digest A (plus reviewer identity, author and change ID). Only eligible human reviewers can approve through that service; the agent, author and pipeline cannot write approval records or grant reviewer eligibility. Protect plan/artifact storage from replacement; keep sensitive plan outputs restricted. GitHub Environment approval is an additional gate, **not** proof that the reviewer approved digest A.
6. **Verify, obtain temporary write access, deploy A.** Before requesting cloud write credentials, the trusted deployment job reads the approval from the protected service and verifies the reviewer's authenticated identity and eligibility, independence from the author, production environment, commit, artifact digest and plan digest against the exact immutable inputs it will deploy. It verifies the approved backup/recovery prerequisite and rollback owner before any write, then rechecks state and the effective operations against A; missing recovery evidence, any changed value, drift affecting A, missing/expired approval or failed verification stops the job and requires a new plan and independent approval. After all checks and the protected production-environment gate pass, only this protected deployment job requests a GitHub Actions OpenID Connect (OIDC) token. The cloud validates that token and lets the job temporarily assume a cloud-managed deployment identity (an AWS role or a Google Cloud service account via workload identity federation), issuing short-lived credentials without storing a long-lived key in GitHub. OIDC itself grants no permissions: a cloud administrator assigns the deployment identity only the actions and resources needed for the approved deployment (Pulumi/Serverless in the stated platform; Terraform only if adopted later), not general-purpose agent tasks. Configure cloud trust for the intended repository, protected workflow and production environment using claims/subject constraints supported by that cloud (and verify the protected ref); protect the workflow and verifier from changes by the author alone, and never expose the deploy role to the agent. OIDC proves the job's origin to the cloud; it **does not prove human approval of A**—the separate approval service and deployment checks do that. The job reads the immutable artifact and plan A, verifies their digests on the bytes it will use, and serializes competing deployments for that environment/scope while it checks state and applies. Deploy only A and the verified artifact; if the tool cannot apply A exactly, stop and re-plan rather than silently applying a different change. The agent never receives write credentials.
7. **Observe and close.** Compare pre/post error rate, latency, queue depth, claim-processing accuracy, tenant-isolation signals and security/audit anomalies for a stated observation window. Assign a named primary and backup on-call owner with paging and escalation; consolidate AWS CloudWatch, Google Cloud and k0s/Firebase signals into a common incident view with tenant/region labels and traceable change IDs. Record deployment outcome and follow-up in Linear. If the threshold is exceeded, halt progression and roll back or forward-fix under the same approval rules; notify partner/privacy contacts when contractual or regulatory triggers apply.

**Rollback is a plan, not a button.** Before production approval, confirm a current, scoped backup/snapshot or documented no-data-risk rationale, recovery access, a feasible restore test/evidence and the named rollback owner. Preserve the previous immutable service artifact and infrastructure state/preview, rehearse reversal in staging, and define who authorizes it. Reverse deployment for stateless code; for Aurora PostgreSQL schema/data changes prefer expand-contract and a tested forward repair or restore decision because rolling back code cannot reverse destructive data migrations. For S3 documents and insurer data, verify backup, retention and restoration boundaries per tenant/region. Confirm recovery-point/recovery-time objectives with service owners; do not invent guarantees. Record who triggered rollback, what changed, and whether data integrity was verified.

### Example: production S3 claim-document access change

A claim-service engineer proposes restricting a production S3 document bucket policy for one insurer in Vietnam. The agent helps reproduce an authorization failure against synthetic objects and drafts a Pulumi change in a pull request. The engineer includes a read-only inventory of affected principals, before/after policy diff, least-privilege access tests, expected region and partner scope, and a rollback policy version. Security and service owners independently inspect the resource preview for accidental public access, cross-tenant grants or denied legitimate claim processing; required checks pass. A named independent production approver approves the exact revision and plan. The gated pipeline assumes its short-lived AWS role, rechecks drift, applies the approved change, then observes AccessDenied rates, claim processing, audit events and S3 access patterns. If legitimate partner access breaks, the on-call owner halts rollout and restores the previously reviewed policy through the controlled path; if an active exposure requires immediate containment, use the emergency path below. A code or policy rollback does not automatically recover data already disclosed; start the incident process for that risk.

## Production incident diagnosis: read-only agent

1. **Triage and evidence.** An alert opens an incident with a named DevOps/on-call owner, affected service, partner and region. The agent reads only pre-authorized, sanitized telemetry (for example bounded CloudWatch and Google Cloud log queries, k0s workload status and deployment history) through the gateway; it cannot retrieve document bodies or unrestricted member records. Log entries are untrusted data, not instructions. The agent correlates recent releases, errors and dependency failures, distinguishes observed evidence from hypotheses, and stops if the safe query scope is exhausted.
2. **Report to DevOps.** The agent writes an incident report to the access-controlled incident record and notifies the named DevOps on-call through the approved integration. Include timestamps, partner/region scope, redacted evidence/query references, confidence, likely cause, impact, safe next checks and whether rollback should be considered. Do not claim a root cause without evidence. If the agent cannot find the fault or lacks permission to continue, say so explicitly; do not retry through another identity or tool.
3. **Approve one additional diagnostic command at a time.** The agent submits the exact proposed command or structured query, target service/account/region/tenant, parameters, time window, expected output, reason and incident ID to a DevOps approval broker. A named DevOps human reviews and approves or denies **each command separately**; no blanket session approval, reusable shell access or automatic approval by an agent. The broker binds a single-use, short-lived approval to the exact request hash and incident, checks that the operation belongs to a strict read-only allowlist, executes it under a separate read-only identity and returns redacted output. It rejects shell metacharacters, arbitrary scripts, unknown plugins, write-capable APIs, database mutations, Kubernetes `exec`/`apply` and unbounded log exports. DevOps approval cannot override these denials. Keep approver identity, request hash, command, result status and access audit; repeat the process for every further command. If safe execution cannot be verified, the human performs a separate investigation outside the agent gateway.
4. **Remediate through humans and the deployment gate.** The agent may suggest a patch, a rollback or a containment plan, but cannot execute one in production. DevOps decides next steps; production changes follow the normal reviewed deployment path or the independently approved emergency operator path below. Neither path grants the agent create/update/delete privileges.

## Emergency production change

Example: audit signals show an insurer's claim documents may be readable by another tenant. On-call declares an incident and creates an incident/change ID; the incident commander identifies the affected region, bucket/principals and first containment action. A **named, independent human** reviews the exact emergency action, scope, expected impact and available backup/rollback or containment-reversal plan and approves it before any production write; the primary or backup on-call approver is paged immediately. If a fresh backup would delay containment or is unsafe, record that limitation and the best feasible recovery path before approval; never claim a backup was taken when it was not. Prefer the pre-tested, narrowly scoped containment runbook through the gated pipeline (for example deny the suspect principal while preserving evidence); prior approval of the runbook is not a substitute for reviewing this incident's specific action. If the pipeline is unavailable, the reviewer approves an incident-bound just-in-time emergency-role activation for a different named operator, with multi-factor authentication, short expiry and the smallest write scope. Record both identities, the reviewed action and approval before activation; monitor the operator's session and compare executed commands against that scope. Never let an agent activate or approve this role. If no independent approver is reachable, escalate to the backup/incident commander; do not perform an unreviewed production write and document the resulting exposure and delay. Preserve evidence, test that access is contained without spreading sensitive data, monitor service impact, and engage security, privacy, the partner owner and legal to decide notification obligations by jurisdiction and contract. Reconcile any console/hotfix change back into Pulumi or other version-controlled desired state, revoke the emergency grant, independently review the diff and incident timeline, and rehearse recovery. Emergency access shortens the route to review; it does not waive named pre-change approval.

## Data, audit and operations

Maintain a per-partner/country data-flow inventory for AWS S3/Aurora, Google Cloud Vertex AI/Gemini, k0s workloads, Firebase Hosting and external model endpoints. Map where content, prompts, embeddings, logs, backups and inference are processed and retained; enforce tenant separation in identity, storage access, application authorization and tests. Decide permitted model endpoints and transfers with privacy/legal and each partner; use minimum necessary fields, redaction/tokenization, encryption in transit and at rest, access logging and retention/deletion schedules. Do not send live medical documents, national IDs, bank accounts or production secrets to an agent or third-party MCP server merely to debug faster. For production AI agents consuming uploaded documents, isolate tools and data by tenant, treat document text as untrusted, enforce authorization at tool/data access boundaries, and monitor unexpected access or egress. Confirm applicable HIPAA obligations and regional rules with counsel; ISO 27001 progress is not certification.

Centralize and protect evidence: identity-provider sign-in and role activation, GitHub reviews/checks/environment approvals and bypasses, OIDC token exchange and cloud audit trails, Pulumi/Serverless/k0s/Firebase writes, access to sensitive records, and deployment/rollback events. Correlate timestamp, actor, incident/change ID, commit, plan hash, artifact digest, partner and region; keep sensitive payloads out of logs. Send to a restricted, tamper-resistant store with role-separated access and retention matched to contracts and law; alert on missing audit feed, direct write, failed gates, unusual egress and emergency-role use. Reconcile logs to changes and periodically test that an investigator can reconstruct who proposed, reviewed, approved and executed a deployment. Define on-call rota, primary/backup, paging severity, acknowledgement/escalation times and runbooks for cross-tenant access, credential theft, data leakage and cloud outage; run tabletop exercises and post-incident reviews. Monitoring is not effective until alerts have owners and response tests.

## Limits, trade-offs and adoption order

- **Velocity vs separation:** independent approval adds latency. Fast read-only diagnosis, reusable checks, small changes and staffed on-call reduce delay; do not substitute an automated agent review for a named human. Emergency access shortens containment time through an independently approved, narrowly scoped action and carries higher audit burden.
- **Coverage gaps:** Pulumi preview may omit runtime behavior, Serverless-generated resources, Firebase configuration, drift or out-of-band cloud writes. Explicitly inventory all deploy paths and run behavioral and negative tests. Cloud administrator/root-level exceptions, compromised approvers, malicious insiders, third-party actions, upstream provider controls and unknown partner terms remain residual risks; no single GitHub gate solves them.
- **Initial priority (contain):** remove routine human/agent production write access; inventory and rotate long-lived CI credentials, replace with OIDC-federated short-lived identities where supported, then revoke old secrets; quarantine unreviewed MCP/plugins; protect production branches/environments; establish a named on-call and emergency procedure. Test denial paths before treating these as complete.
- **Next (make repeatable):** enforce isolated checks and protected configuration files, partner/region data classifications, reproducible artifacts and plan-bound approvals; centralize audit correlation and alert ownership; rehearse a routine change and a rollback.
- **Then (measure and expand):** close k0s/Firebase and remaining out-of-band deployment paths, add phased releases and policy-as-code coverage, partner-specific residency checks, access reviews, incident exercises and regular evidence sampling. Prioritize gaps by blast radius and evidence, not a claimed compliance badge.

**Self-review:** A branch gate without cloud-side denial would leave direct production access open; the design adds cloud identity restrictions and a negative test.
